# Fresh Semaphore on TrueNAS (candidate; not deployed)

This stack deliberately uses fresh state, not migration of the old Semaphore DB. Official Semaphore v2.20.23 (November 10 release) and supported PostgreSQL 16.16 (November 12 security release) are selected; do not change DB major versions automatically. PostgreSQL is not published to the host. Semaphore is published on a specifically chosen private LAN address, subject to checking port availability and firewall/ACL restrictions. Use trusted HTTPS through the approved reverse proxy before sending credentials over the network. No public port forwarding or Funnel.

The already-created config and database datasets must be mounted. The one-shot prepare service is restricted to the config dataset, has no network, and creates two private subdirectories owned by UID 1001 (the upstream Semaphore user). It refuses existing symlinks or unexpected owners; it does not recursively change ownership. Verify actual TrueNAS ACL behavior, successful prepare exit and application startup. PostgreSQL initializes its own pgdata subdirectory. No host shell, privileged container, Docker socket, arbitrary bind mount, or old database reuse.

Private deployment requires three unique values: database password, administrator password and 32-byte base64 access-key encryption key (generate locally, retain in a password manager). Select a private LAN bind address reachable by the existing management container. Keep these values out of Git and model output. Compose interpolation requires the variables to exist at render time; the TrueNAS YAML editor is not a guarantee of .env support. Use a privately rendered YAML with an approved deployment method. Never commit the rendered YAML. Back up secrets and config securely; changing the encryption key can make existing stored keys unrecoverable.

Before production use: create recursive periodic snapshots of appdata; establish independent backup of config/data and consistent pg_dump archives, then verify restoration. Old nightly rsync does not cover new appdata. Keep the old Semaphore service available until login, API token creation, representative safe task and MCP connectivity are verified. The old automation inventory, keys and template references need review before recreation; do not assume project IDs will match. Never self-redeploy the active MCP tunnel.
